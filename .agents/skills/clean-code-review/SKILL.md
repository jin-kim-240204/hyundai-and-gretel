# 클린 코드 리뷰 규칙

PR의 변경분과 관련 호출부·테스트를 읽고 적용되는 규칙만 골라라. 코멘트마다 **위치 → 깨지는 상황 또는 읽기 어려운 이유 → 가장 작은 개선**을 적어라. 검증된 결함, 정책 질문, 선택 개선을 구분하라.

리뷰 요청만으로 구현 코드를 수정하지 않는다. 아래 규칙은 프로젝트 리뷰 기준이며 공식 Pleos 의무와 구분한다.

## 이름과 계약

1. 값의 출처나 단위가 판단에 영향을 주면 이름에 드러내라. 예를 들어 `receivedElapsedMillis`와 `createdAtUtcMillis`를 구분하라.
2. 같은 타입의 인자를 바꿔 넣어도 컴파일되면 명명 인자를 써라. 혼동이 여러 호출부에서 반복되면 타입으로 구분하라.
3. 함수가 값을 반환하면 이름으로 그 값이 무엇인지 알 수 있게 하라. 수량을 반환하는 `get()`은 `countByPrize()`처럼 구체화하라.
4. `Boolean`의 양쪽 의미가 호출부에서 모호하면 이름을 먼저 고쳐라. 호출자가 구분해야 할 결과가 더 있으면 결과 타입에 표현하라.
5. 함수를 읽어야만 외부 상태를 바꾼다는 사실이 보이면 이름이나 계약에 그 동작을 드러내라.
6. 숫자가 제품 정책이면 정책을 소유하는 곳에서 이름을 붙여라. 값이 같은 두 숫자도 서로 독립적으로 바뀌는 정책이면 따로 관리하라.

## 함수와 책임

7. 한 함수에서 다른 시점에 실행될 작업이 중첩되면 진입점에서 호출 순서가 보이게 하라. SDK 등록과 등록 후 콜백 처리가 대표적이다.
8. 예외 조건이 정상 흐름을 여러 겹 감싸면 먼저 반환할 수 있는 조건을 위로 올려라.
9. 같은 정책을 여러 곳에서 판단하면 한 곳에서 정의하라. 코드 모양만 비슷할 때는 두 정책이 함께 바뀌는지 먼저 확인하라.
10. 표준 함수나 한 호출을 그대로 감싼 래퍼를 보면 호출자가 얻는 역할을 확인하라. 보존할 검증·정책·테스트 경계가 없다면 직접 호출하라.
11. 인터페이스가 있으면 실제로 구현을 바꾸는 호출자나 테스트를 찾아라. SDK를 가짜 소스로 교체하는 `LocationSource`는 그 쓰임이 있다.
12. 한 기능에서만 쓰는 타입과 컴포넌트는 그 기능 가까이에 두고 가시성을 좁혀라. 공유가 생기면 함께 쓰이는 범위로 옮겨라.
13. 주석이 코드의 동작을 반복하면 이름이나 구조를 고쳐라. 코드에서 알 수 없는 정책의 이유나 SDK 제약은 주석으로 남겨라.
14. 스코프 함수나 체이닝을 읽을 때 수신 객체나 반환값을 추적해야 하면 중간 값에 이름을 붙여라.

## 상태와 Compose

15. 기존 상태에서 값이 정해지면 그 상태에서 계산하라. 따로 저장할 때는 갱신·무효화 조건을 확인하라.
16. 여러 플래그가 항상 함께 바뀌고 일부 조합이 불가능하면 가능한 상태를 타입으로 표현하라. 독립적으로 바뀌는 사실은 각각 소유자를 두어라.
17. 화면 상태가 재생성 후에도 필요하면 새 화면이 현재 값을 다시 읽도록 하라. 한 번만 처리할 행동은 그 실행 조건과 수명을 명시하라.
18. Composable이 화면을 그리면서 SDK 등록이나 DB 쓰기까지 하면 사용자 이벤트나 수명에 맞는 Effect로 실행 시점을 옮겨라.
19. Effect를 보면 키가 유지될 때와 바뀔 때 각각 어떤 작업이 재실행·취소되는지 확인하라.
20. 필수 클릭 콜백을 생략해도 컴파일되고 버튼이 조용히 동작하지 않으면 호출자가 콜백을 명시하도록 하라.
21. 여러 호출자가 크기나 배치를 달리해야 하면 `Modifier`로 제어할 수 있게 하라. 터치 영역처럼 컴포넌트가 지켜야 할 조건은 내부에서 유지하라.

## 실패와 수명

22. 조회 실패 후 쓰기로 넘어가면 데이터 없음과 저장소 오류를 구분하라.
23. `runCatching`을 보면 어떤 예외가 값으로 바뀌고 호출자가 어떻게 처리하는지 확인하라. 코루틴의 `CancellationException`은 전파하라.
24. 자원을 등록하거나 열면 정상 중지와 중간 실패 양쪽의 해제 경로를 확인하라. 해제 중 일부가 실패해도 남은 정리가 필요한지 확인하라.
25. 콜백을 나중에 처리하면 중지·재시작 사이에 들어온 이전 콜백을 검토하라. 상태를 바꾸기 직전에 현재 세션인지 확인하라.
26. SDK에 대한 추상화를 추가할 때는 공식 계약, 실제 배포물에서 확인한 사실, 앱이 정한 정책을 구분하라.
27. 단계마다 실패 원인이 다르면 로그에서 실패한 작업을 구분하라. 포그라운드 전환 실패와 SDK 등록 실패는 조사할 곳이 다르다.

## 검증

28. 비동기 테스트에서는 완료를 알려주는 상태나 결과를 기다려라. 로딩 전과 완료 후의 기대값을 따로 검증하라.
29. 재시도·중복 방지 테스트는 실제 실행 횟수와 저장 결과를 단언하라. 첫 요청과 마지막 요청의 값 비교만으로 재시도를 확인하기 어렵다.
30. 특정 시점에 일어나야 하는 동작은 그 구간에 관찰하라. 화면 복귀 후 위치가 있다는 사실과 화면 밖에서 새 위치가 들어왔다는 사실을 구별하라.
31. 시간·난수에 따른 정책을 테스트할 때는 입력을 고정하라. 경계값과 그 바로 바깥에서 기대 결과를 확인하라.
32. 테스트가 검증하려는 동작을 빼도 통과한다면 관찰 지점을 고쳐라. 가짜 소스 검증과 실제 SDK 검증은 각각 무엇을 확인했는지 기록하라.
