# Ponytail 브랜치 전체 리뷰

이 변경의 역할: main(c5fd034) 이후 작성된 위치 쪽지 시연 코드 전체를 검토했다. 단일 Pleos 에뮬레이터에서 합성 위치를 수집하고, 과거 위치에 쪽지를 저장한 뒤 B가 접근하면 수신한다. 현재 리팩터링은 후보 선택과 수신함 조회를 정리한다.

## 반드시 수정

1. **후진에서 먼 쪽지가 접근 등록 한도를 차지함** (`DemoController.reconcile`, 수정 전 255~264행; 현재 `notes/RoadNote.kt:39`)
   - 역할: 주변 후보에서 최대 16개 SDK 접근 등록 대상을 고른다.
   - 문제: 현재위치 0m, 후진 쪽지 -10~-170m가 있으면 progress 차이 오름차순이 -170m부터 고른다. 17번째인 가장 가까운 -10m가 등록에서 빠진다. 기존 선택식을 보존한 상태에서 추가한 회귀 테스트가 실제 실패했다.
   - 최소 수정: 후보 선택을 `proximityCandidates`로 옮겨 부호를 반영한 전방거리로 정렬한다. 수신 판정도 같은 `distanceAhead`를 사용하여 방향 계산 중복을 없앴다.
   - 그대로 두면: 여러 쪽지가 있는 후진 시연에서 가장 먼저 접근할 쪽지의 등록이 늦어진다.
   - 조치: 수정 완료. 양방향 17개 후보, 16개 우선순위, 자기 제보/기수신/만료/후방/반대 방향/신선도 검증 단위 테스트 PASS.

## 수정 권장

2. **수신함 JOIN 후 같은 쪽지를 건별로 다시 조회함** (`data/RoomNotes.kt:39`, `data/NoteDatabase.kt:54`)
   - 역할: 수신 이력과 원본 쪽지를 묶어 화면에 보낸다.
   - 문제: 기존 쿼리는 JOIN한 쪽지 열을 버린 뒤 N개 수신마다 N개의 byId 쿼리를 추가한다. 목록 읽기와 각 쪽지 읽기의 시점도 달라진다. 소규모 시연에서 성능 장애가 측정됐다는 주장은 하지 않는다.
   - 최소 수정: 기존 JOIN이 쪽지 열·수신자·별칭을 둔 수신시각을 함께 반환하도록 한다. 도메인 유효성 검증과 수신시각/ID 정렬은 유지한다.
   - 그대로 두면: 수신함 갱신마다 불필요한 DB 작업과 중첩 nullable 변환을 유지해야 한다.
   - 조치: 수정 완료. 두 쪽지의 순서/각 수신시각, 사용자·시나리오 격리, 부모 삭제 후 빈 수신함을 기존 Room 계측에 추가했고 PASS. 스키마/마이그레이션 변경 없음.

## 그대로 둔 결정

- `RoadNoteRepository`: 한 구현체지만 기존 설계 §5.7에 명시된 저장소 교체 계약이다. 삭제 대상으로 판단하지 않았다.
- `DemoController`: 세션 수명과 직렬쓰기를 소유하는 구조는 유지하고, Android 없이 검증할 후보 선택만 분리했다. 파일 크기만 줄이는 이동이나 새 계층은 추가하지 않았다.
- H3 고정 경로·등록 16개·SDK 준비 지연의 `shortcut:`은 이미 한계가 문서화된 시연 선택이다. 실차/대규모 서비스로 확대하지 않았다.
- 기존 린트의 버전·미사용 템플릿 리소스·표기 제안은 이 브랜치의 동작 결함으로 분류하지 않았다. 새 의존성/버전 업그레이드 없음.

- PASS: debug/release assemble, assembleDebugAndroidTest, lintDebug, harness --build, Studio build_project.
- PASS: Pleos 2.1.0/Android14/user10 RoomNotesTest+SessionGuardTest 3개(0.516초).
- PASS: verify_location_demo.py의 실제 SDK A 저장→B 접근→중복 수신 방지, DemoFlowTest 1개(59.055초), FLOW_PASS.
- 린트는 오류 없이 종료했지만 기존 경고 48개가 있다. 그중 Lifecycle 린트 2종은 도구 API 불일치로 실행되지 않았다. 린트 종료 성공을 해당 두 규칙 검증으로 해석하지 않는다.
- NOT_TESTED: 실제 privacy 차단/null/error 콜백 주입, 실차, 전체 폼팩터, SDK 최대 등록 한도. 기존 미검증을 이번 결과로 덮지 않는다.

판정: 1·2 수정 및 해당 회귀 검증 완료. 전체 SDK/출시 적합성 판정은 하지 않는다. 첫 테스트 삭제 커밋만 푸시했으며 후속 리팩터링은 검토 가능한 미커밋 변경으로 남겼다.

실행 부하: Gradle과 Pleos 에뮬레이터 실행이 겹쳤고 사용자가 팬 증가를 알렸다. 통합 테스트 통과 직후 이번 작업이 실행한 emulator를 종료했다. 종료 후 ps에서 Chrome 렌더러 104.3%, Studio 14.8%가 관측됐다. 종료 전 프로세스 부하/CPU 온도는 측정하지 않아 발열 기여도를 확정하지 않는다. 이후 무거운 검증은 추가 실행하지 않았다.

후속 요청: 사용자가 리팩터링 커밋·푸시를 승인했다. 위 검증 이후 운영 코드 변경 없이 정적 검사와 diff를 재확인하고 현재 변경을 보존한다. 이 리팩터링이 새 spec-driven 작업의 최종 참고 구현이며 신규 기능의 검증을 대신하지 않는다.
