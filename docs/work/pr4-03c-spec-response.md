## 정책 쟁점과 권고

### 1. 준비/첫 표본 대기 중 버튼 활성 — 현 제안 유지 권고

03-c §3은 활성 수집 세션이고 저장 중이 아니면 클릭을 허용해요. 클릭 → Repository의 anchor 선택 → 표본이 없으면 LOCATION_UNAVAILABLE이며 DB 쓰기는 없어요. Repository도 현재 이 순서로 동작해요. 따라서 버튼 활성은 위치 저장 가능 보장이 아니라 테스트 요청 가능을 뜻해요.

30초 대기나 UI 신선도 상태를 추가하지 않는 편을 권해요. 첫 신선한 표본부터 짧은 이력으로 저장한다는 기존 03 계약과 맞고, UI에 버퍼 정책을 복제하지 않아요. 첫 위치 전 클릭이 실패할 수 있는 것은 debug 진단 UI의 의도된 결과로 기록하면 충분해요. 확정 결함은 아니며 독립 리뷰에서 이 의미를 확인하면 돼요.

게시 초안:

> 첫 위치가 오기 전에도 활성 수집 세션이면 테스트 제보를 누를 수 있는 방향을 유지하는 게 좋겠어요. 이 버튼은 저장 성공을 보장하는 상태가 아니라 기존 제출 경로를 확인하는 진입점이고, 표본이 없으면 Repository가 위치 확인 실패로 끝내며 DB에는 쓰지 않아요. UI에 별도 30초 대기나 신선도 판정을 추가하지 않고, 첫 표본 전 실패도 의도한 동작으로 확인하려고 해요. 아직 구현 전이에요.

### 2. 결과 보존은 서비스 인스턴스 수명까지 — 조건부 수용 권고

03-c §3의 같은 서비스 재연결 시 Saved/Failed 재관찰, 새 서비스에서는 Idle 정책은 서비스 소유 결과라는 기존 03 계약과 맞아요. DB 원본의 영속성과 결과 문구의 영속성은 별개예요. Repository는 StateFlow에 결과를 보관하고, 서비스가 이를 소유해요.

중지 후에도 화면이 bind 중이면 stopSelf만으로 객체가 즉시 소멸했다고 해석하지 않아야 해요. 스펙이 이미 이 차이를 명시해요. 따라서 중지→현재 연결에서 Saved 관찰, 실제 서비스 소멸→새 연결에서 Idle을 구분해 검토하면 돼요. 성공 복원용 DB 조회나 결과 소비 큐는 추가하지 않는 편을 권해요. Android 실제 콜백/수명 순서는 이번 검토로 보장하지 않아요.

게시 초안:

> 마지막 결과는 같은 서비스 인스턴스가 살아 있는 동안 관찰하고, 실제 종료 뒤 새 서비스에서는 Idle로 시작하는 범위가 적절해 보여요. 저장된 원본은 Room에 남지만 성공 문구까지 영속 복원하는 요구는 이번에 없어요. 특히 stopSelf 호출과 객체 소멸을 같게 취급하지 않고, bind가 유지되는 동안에는 기존 결과를 계속 관찰하도록 구분하려고 해요. 실제 Android 연결·종료 순서는 기기 실행을 하지 않아 미검증으로 남겨요.

### 3. 같은 연결의 상태·동작 교체와 테스트 경계 — 수용 권고

현재 ViewModel은 추적 StateFlow만 전환하고 서비스 Binder는 제출 상태·진입점을 이미 제공해요. 03-c는 같은 연결에서 두 상태와 제출 참조를 함께 교체해야 해요. A 연결 해제→B 연결→늦은 A 갱신/클릭에서 B 상태와 A 동작이 섞이면 안 돼요. 클릭 직전 현재 연결 확인, 이전 구독 취소, 새 연결의 현재 값 관찰이 필요한 최소 범위예요.

production에서 사용하는 작은 연결 전환 경계를 Fake로 검증하는 안에 동의해요. 테스트만의 서비스 종료 로직을 새로 작성하거나 범용 ConnectionManager를 만드는 것은 피하는 편이 좋아요. SDK 오류 후 수락 저장 보존은 기존 Repository/서비스 수명 규칙을 대상으로 확인하고, Fake PASS를 실제 Binder·알림·마지막 unbind 이후 생존의 증거로 확대하지 않아야 해요.

게시 초안:

> 추적 상태와 제출 상태, 제출 동작은 같은 서비스 연결에서 함께 교체하는 방향으로 반영하면 좋겠어요. A 해제 뒤 A가 갱신돼도 화면이 바뀌지 않고, B 연결 뒤에는 B의 현재 상태와 동작만 쓰는지 production 연결 로직을 Fake로 확인하려고 해요. 저장 수명 검증도 기존 종료 판단을 사용하고 테스트에 규칙을 복제하지 않겠어요. 별도 범용 계층은 추가하지 않고, 실제 Binder/SDK/서비스 수명은 JVM 검증과 구분해 미검증으로 남겨요. 아직 수정·검증 전이에요.
